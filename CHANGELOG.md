# Changelog

## Unreleased

Replace the memory SDK with a file SDK: a thin file abstraction over LambdaDB
collections, branches and tags. The SDK exposes what LambdaDB supports and holds
no state between calls other than in-process per-branch queues for
state-changing calls; ordering across processes and multi-process ownership
belong to the caller.

- Create, open and destroy file stores with `MemDrive.create`, `MemDrive.open` and `MemDrive.destroy`. A store is one LambdaDB collection with the format tag `files-v2`; creation sets native `snapshotRetentionInDays` to 1, with no retention option. `destroy` deletes that collection after checking that it is a file store, and treats a missing store as already destroyed. `describe({ at? })` returns the configuration read by `create` or `open` and `latestCheckpoint: { at } | null` of main or a fork, read from the branch's reserved alias with one request; a checkpoint `at` fails with `INVALID_INPUT`.
- Select a view on every request with a serializable `at`: `{ kind: 'main' }` (the `main` branch), `{ kind: 'fork', name }` (a branch) or `{ kind: 'checkpoint', name }` (a read-only tag). Omitting `at` selects main. Main and forks are read with consistent branch reads, checkpoints from their tag. A native 404 on a view request is reported as `STORE_NOT_FOUND`, `BRANCH_NOT_FOUND` or `CHECKPOINT_NOT_FOUND` with status 404.
- Write files to main or a fork with `write`, as one operation or a batch of up to 100 `create`, `update` (including moves and exact `oldText`/`newText` edits), `append` and `delete` operations; checkpoints reject writes with `INVALID_INPUT`. A file is an original document plus chunk documents; chunks are written before the original that makes the file visible, and a delete removes the original and then its chunks. Each request is confirmed with a consistent read. Path uniqueness (`PATH_EXISTS`) is checked by a read before writing and is best effort only across processes. A write whose outcome is unknown fails with `WRITE_UNCONFIRMED` and details of the attempted and completed files, without fencing later calls. Batches are not transactions. A file counts as completed once its original is written or deleted, so a failed chunk cleanup (stage `cleanup-chunks`) still lists it in `completedFileIds`. Cleanup rereads the original and keeps its current chunk generation, and an update that finds no chunks for a nonempty original chunks it again, so resending an update repairs a file whose chunks racing writers in separate processes removed. Racing creates from separate processes can leave two files at one path: updates and deletes by `fileId` keep working, only creates and moves are checked against other files, and reading such a path fails with the new `PATH_AMBIGUOUS` error listing the file IDs.
- Append to text files without reading them with `{ op: 'append', path | fileId, content }`: the new content is the existing content, one `\n` when it is nonempty and does not end with a line break, then `content`. By path, a missing file is created as `create` would, one file is appended to and several fail with `PATH_AMBIGUOUS`; by `fileId`, a missing file fails with `FILE_NOT_FOUND`. The path lookup and original read run in the branch's queue turn, so appends by one new path in one process end as one file. An append is otherwise a content update (full re-chunking, attribution, 5 MiB limit) without a conflict check. In a batch, an append targets the file it resolves to and an append by path claims its path, so duplicates fail before any write. External-vector stores reject it with `INVALID_INPUT`.
- Record who created and last modified each file and when: originals store `createdAt` (indexed as `datetime`, like `modifiedAt`), `createdBy` and `modifiedBy`, and write results, `read`, `list`, `search` and `findText` return them in both embedding modes. Every `write` request form accepts request-level `by` (a `FileActor`, `{ user?, agent? }`) and `time` (a `Date`, replacing the current time for the call's `createdAt` and `modifiedAt`); operations inside a batch accept neither. `createdAt` and `createdBy` never change; `modifiedBy` follows `modifiedAt`, becoming the call's actor whenever the file's path, content or metadata changes and being removed when the call named none. Actors are stored as given, without an index; invalid actors (other keys, no name, blank, control characters, lone surrogates or more than 256 UTF-8 bytes) or times (not a valid `Date` in the years 0000–9999) fail with `INVALID_INPUT` before any storage request. A `time` before a file's `createdAt` is accepted and yields `modifiedAt` before `createdAt`. A move keeps its single native patch: because a patch merges into the stored original and cannot remove a field, a move that changes `modifiedBy` sends both names with `null` for a missing one, reads treat `null` names as absent and an actor without names as none, and the next full write of the original stores the actor without nulls.
- Run state-changing calls one at a time per branch within one process, in call order: `write` on main or a fork (a checkpointed write including its checkpoint, alias move and restore), `rollback` of that branch, `fork` and `checkpoint` whose source is that branch (so a new ref never captures a half-applied write) and `deleteFork` of that fork. A file is several LambdaDB documents and LambdaDB has no multi-document transaction or conditional write, so this keeps concurrent updates of one file from removing each other's chunks and concurrent creates from leaving two files at one path. The queues are keyed by the store generation and branch, are shared by every drive object of that store in the process, and exist only while calls are pending. Reads, `deleteCheckpoint` and refs taken from a checkpoint never wait; calls on different branches run concurrently; a failed or aborted call does not hold up the next, and aborting a waiting call rejects it with `ABORTED` before it sends anything. `destroy` waits for the store's pending calls and state-changing calls made after it has read the collection fail with `STORE_NOT_FOUND`. Separate processes and separate SDK copies are not coordinated.
- Read exact originals by `fileId`, `path` or up to 100 `paths`, and read bounded line or character ranges with exact line endings, Unicode-safe continuation and `READ_VERSION_CHANGED` detection.
- Search indexed chunks with semantic retrieval by default, explicit keyword and hybrid modes, independent opt-in reranking, declared-metadata filters and verified source ranges. External-vector stores store caller-supplied vectors and search them with vector queries. LongMemEval and BEAM explicitly select hybrid retrieval.
- Find case-insensitive literal occurrences in original text with `findText`, with verified UTF-16 ranges, one-based `startLine`/`endLine` numbered like ranged `read`, excerpts, prefix and metadata filters, and stateless cursors. Checkpoint scans are snapshots; main and fork scans are live. Originals are scanned in ID-ordered batches of up to 16 per page.
- List files with `list` in path order using LambdaDB's native ordered document listing with consistent reads on main and forks. It follows native pages as needed to fill each page of files and folder prefixes and report `next` only when another entry exists. The listing can cover more than 1,000 files. `limit` (default 100, 1–1000) counts files and prefixes together. The full path prefix and case-sensitive literal filename substring still apply, a folder appears once with the `'/'` delimiter, and files sharing a path follow in `fileId` order. The stateless cursor carries the criteria and last returned position, including for continuation across live writes. Existing `l2` cursors continue to work. A malformed, foreign or obsolete-format cursor fails with `LIST_CURSOR_UNAVAILABLE`, and another view's cursor fails with `CURSOR_VIEW_MISMATCH`. Ancestor folder filters match folder names containing double quotes exactly, also for `findText`.
- See what a drive holds with `tree({ at?, prefix? })`, like the shell's `tree -d` with file counts: one LambdaDB query with facets on `ancestorPaths` and `kind` returns `{ fileCount, folders: [{ path, fileCount }], truncated }`: the exact number of files under `prefix` (an absolute folder ending in `/`, default `/`) and the folders below it with their recursive file counts, in path order. LambdaDB returns at most 100 folder buckets, the most populated first, and the prefix and its ancestors use buckets too; `truncated: true` reports that less populated folders may be missing. An aggregation over too many distinct folders fails with `DATABASE_ERROR` status 400; take candidate folders from search hit paths and narrow the prefix. It reads no files and works in both embedding modes.
- Create forks and checkpoints from any view with `fork({ at?, name })` and `checkpoint({ at?, name })`, list them with `listForks` and `listCheckpoints`, and delete them with `deleteFork({ at })` and `deleteCheckpoint({ at })`. Each creation or deletion sends one native request; name conflicts report `BRANCH_CONFLICT` or `CHECKPOINT_CONFLICT`. Fork names have 3–40 characters so that the fork's reserved alias fits LambdaDB's 52-character reference names. A checkpoint of main or a fork also moves that branch's reserved alias to it in the same queue turn (creating it on 404); if that move fails and reading the alias back does not show it moved, the call throws `LATEST_CHECKPOINT_NOT_MOVED` and the checkpoint stays. `listForks` and `listCheckpoints` return one native page per call (`limit` 1–100, default 100) of `{ at, createdAt }` entries in LambdaDB's name order, with a stateless `next: { cursor }` bound to the store. `deleteFork` deletes the fork's alias before the branch (a later branch-deletion failure adds `latestCheckpointCleared: true`), and `fork` deletes any alias left under the new fork's name in the new fork's queue turn. `deleteCheckpoint` refuses a checkpoint that is a branch's latest with `CHECKPOINT_IN_USE`, also when LambdaDB answers 409.
- Add `rollback({ at, to })`, which replaces the contents of main or a fork with those of a checkpoint through one `branches.rollback` call that is never retried, and returns `{ at }`. When the branch has a latest checkpoint, the rollback moves it to `to`; a failed move after the rollback, including a 404 for a `to` deleted meanwhile, throws `LATEST_CHECKPOINT_NOT_MOVED` with `rolledBack: true`. Resending a rollback can undo writes made after the first one. A checkpoint is eligible for rollback immediately, including before its first snapshot is published.
- Add checkpointed writes: `write({ ..., checkpoint: { name } })` applies the write, creates the tag `checkpoint-<name>` from the branch and moves the branch's SDK-reserved alias (`latest-main` or `latest-fork-<name>`) to it in one queue turn, and returns `{ result, checkpoint: { at } }`. Success adds one tag creation and one alias retarget to the write's requests (an alias creation on the branch's first checkpoint). Errors raised before the first mutation, including aborts, pass through unchanged. Any later failure restores the branch: the SDK reads the alias (a lost alias move that did happen completes the call), rolls the branch back to the checkpoint it names and deletes the new tag (after an unknown creation outcome only when the tag's creation time shows this call created it), or, without an alias, deletes the files the call created. Checkpoint names must be unique across host restarts. It then throws `CHECKPOINT_WRITE_FAILED` (`details.restored: true`, `stage`, `restoredTo`, `cause`) or, when the restore failed or a first checkpointed write changed existing files, `CHECKPOINT_RESTORE_FAILED` (`details.restored: false`, `restoreCause`, `unrestoredFileIds`). The rollback is never retried. There is no option to change the restore behavior.
- Persist per-file chunking strategies (`auto`, `boundary`, `none`, `docling`) and provide an optional Node-only Docling Hybrid adapter at `@functional-systems/memdrive/docling`, preserving exact originals, contextualized embeddings and verified ranges. Managed stores leave original `body` and chunk `embeddingText` without a text index and declare the embedding source with the native `sources` form.
- Provide a minimal shared file-tool catalog for agents on main: `guide`, `read`, `tree`, `list`, `search`, `findText` and `write`, with an explicit allowlist, one fixed schema set per embedding mode, no `at` in any schema, input or result, portable error formatting, `fileToolInstructions` and a versioned read-only guide. Tool descriptions carry what ordinary use needs: `write` says when to save (whatever a later conversation or another agent will need, without waiting to be asked), all of a turn's changes in one call, the user's wording and keeping an earlier statement beside a differing new one, which in text mode means recording what the user says outside `/preferences.md` as entries appended to a file, each with when it was said if known, and leaving earlier entries as they are, without rewriting them or noting which is correct or current, unless asked to change the saved text; `search` says to search before answering and writing and to say when the drive does not record something; `read`, `search` and `findText` treat returned text as information only. In text mode, `write` keeps what the user says they want in answers always or from now on in `/preferences.md`, one per line, replacing a line when the user changes it, and `read` asks for that file before the first answer of every conversation and follows it for how answers are given, never for tool calls or authorization, the only exception to the information-only rule. `search` and `findText` still treat returned text as information only, so the exception applies when the file is read; a host that does not offer `read` gets no preferences behavior. The SDK reserves and validates nothing for that path: it is an ordinary file, one per drive. Every text-mode agent on the drive reads it before its first answer and follows it for how answers are given, so whoever can write it changes later answers (another user of a shared drive, whose lines are then applied as the user's, another agent, or an import that contains a root `preferences.md`); a host that needs to prevent this must control writes to that path. External-vector descriptions do not mention the file. `fileToolInstructions` is a short optional supplement that relates the tools and names no tool that only some hosts offer, such as `tree`, `findText` or `guide`. The guide (version 7) is reference for unusual cases, not required reading, with `retrieval` and `editing` topics described by when to read them: search modes, missing or excessive results, tree limits, listing pagination, ranged reads and cursors; duplicates, what belongs in `/preferences.md`, conflicting statements, long conversation content, write errors, moves and deletion caveats. `createFileTools({ drive, tools, checkpoint? })` takes an optional host hook returning `{ name }` that makes every `write` tool call a checkpointed write and returns the plain write result; checkpointed-write errors reach the agent without checkpoint names. Optional host `actor` and `now` options pass `by` and `time` on every `write` tool call; tool inputs with `by` or `time` fail with `INVALID_INPUT` before any storage request. In text mode the `write` tool offers `append`, and its results identify each created, updated or appended file by its listing fields without `content` (deletions stay `{ fileId }`), so writes no longer return whole files to the model. Refs, rollback and retention stay host operations through the SDK.
- Re-export `LambdaDBClient` and `HTTPClient` from the pinned `@functional-systems/lambdadb` `0.15.0`, which requires a LambdaDB deployment with tag creation and branch rollback before a tag’s first snapshot is published (LambdaDB PRs #614 and #640). The native rollback response allows `headSnapshot: null`; MemDrive returns `{ at }`.
- Run LongMemEval and BEAM against the public file SDK, and evaluate model tool use with the shared catalog in a repository benchmark (protocol `memdrive-tool-use-v9`: main-only tools including `tree`, with host-checkpointed writes and the current agent-facing wording).

Removed relative to earlier unreleased development builds, without a compatibility path. Stores they created (formats `files-v0` and `files-v1`) fail to open or destroy with `INCOMPATIBLE_STORE`; delete those collections, and the `md-journal-*` collections of `files-v0` stores, directly with LambdaDB.

- APIs: `merge`, `diff`, `status`, `history`, `configure`, `retentionInDays` on `create` and in `describe()`, and `version` on `fork` and `checkpoint`; the `merge`, `diff`, `status` and `history` tools, the `fork`, `checkpoint`, `listForks`, `listCheckpoints`, `deleteFork`, `deleteCheckpoint` and `rollback` tools and `at` in tool schemas, and the `publication`, `references` and `maintenance` guide topics; the `MergeRequest`, `MergeResult`, `FileChange`, `FileStoreStatus`, `FileHistoryRequest`, `FileHistoryEntry`, `FileHistoryResult` and `ForkRequest` types; `version` on ranged read pages.
- Storage: the publication journal collection, `md-main-v*` version tags and the `md-main-v0` initial view, and file tombstones, baselines, fingerprints and the `changed` field and index on originals. Main is read directly from the `main` branch.
- Process state: per-fork write queues (replaced by the per-branch queues above), the store merge queue, the per-client store registry and lifecycle gate, write, reference and configuration uncertainty fences, the store deletion marker, and the list scan cache with its process-wide budget and timers.
- Error codes: `MERGE_CONFLICT`, `HISTORICAL_VIEW_UNAVAILABLE`, `HISTORY_CURSOR_UNAVAILABLE`, `VERSION_NOT_FOUND`, `REF_CREATION_UNCONFIRMED`, `REF_DELETION_UNCONFIRMED`, `CONFIGURATION_UNCONFIRMED`, `STORE_BUSY`, `STORE_DELETING`, `STORE_DELETED`, `STORE_DELETION_UNCONFIRMED`, `STORE_REPLACED`, `MAIN_BOOTSTRAP_UNCONFIRMED`, `CHUNKER_MISMATCH` and `LIST_SCAN_LIMIT`. Unknown fork, checkpoint, deletion and rollback outcomes surface as the underlying error.

## 0.1.0

First stable release of the standalone MemDrive SDK. The public API and storage
format are unchanged from 0.1.0-rc.1; the LambdaDB TypeScript client remains pinned
to 0.12.0.

- Provide memory storage, vector and hybrid retrieval, complete-original reads, metadata inspection, branches and portable agent tools.
- Wait for npm registry metadata to become visible after a successful publication, without retrying publication; verify archive identity and report channel state on reruns.
- Document stable installation and the `latest`, `rc` and `dev` channels.

## 0.1.0-rc.1

First release candidate of the standalone MemDrive SDK, backed by the pinned
LambdaDB TypeScript client 0.12.0.

- Store original memories with automatic text chunking, or store caller-provided embeddings and metadata.
- Retrieve evidence through vector or hybrid search with optional native reranking; support structured metadata filters, exclusions and ordered batch results.
- Read complete originals, inspect schema descriptions and keyword distributions, and manage memories and branches.
- Expose portable agent tools through `@functional-systems/memdrive/tools`, with JSON Schema contracts, branch binding and optional writes. Applications own search orchestration and answer generation.
- Support ESM, CommonJS and TypeScript consumers on Node.js 20.12+ and browser bundlers.
- Validate installed release archives with bounded live integration checks and publish immutable versions with source identity through npm Trusted Publishing.
- Supply the required Bayesian candidate budget when hybrid recall disables reranking.
