# Changelog

## Unreleased

- Re-export `LambdaDBClient` and `HTTPClient` from the pinned `@functional-systems/lambdadb`, so hosts construct the client from `@functional-systems/memdrive` and always use the version the SDK requires.
- Require LambdaDB client `0.14.0` and a LambdaDB deployment that creates a tag on a branch before its first snapshot commits (LambdaDB PR #614). Client `0.13.0` cannot parse the null snapshot fields such tags report, so a first merge or a fresh checkpoint failed as an unconfirmed outcome. A checkpoint's findText cursor is now bound to the tag's creation time only, because its snapshot ID changes from null when the snapshot is published. A merge no longer retries a definite rejection of its target tag for up to 120 seconds: the merge pauses with `MERGE_RESUMABLE`, and the `MERGE_TARGET_NOT_READY` error is removed.
- Export `fileToolInstructions` from the SDK for hosts to share with agents. Clarify the guide's editing conventions and document how to recover a deleted file from a retained version.
- Merge directly from the working fork instead of from an internal capture tag. A merge no longer creates, confirms, retains or releases a `merge-capture-<id>` tag: it reads its source from the fork branch with the fork's own consistent reads, and the only tag it creates is the target main version. The fork is held still until its merge is settled, meaning a terminal outcome and, for a publication, confirmed source bookkeeping. While the merge runs, a write, `diff`, fork or checkpoint creation from that fork, or another merge of it waits in the fork's queue and runs after it. If the merge ends unfinished (`MERGE_RESUMABLE`, an unconfirmed journal record or a content mutation of unknown outcome), every write to that fork fails with `MERGE_BLOCKED` and the blocking `details.requestId` until the same request is retried to completion or recovery settles it; reads, `diff` and creating a fork or checkpoint from it stay available. A new process reads the journal head before its first write to each fork and afterwards relies on its own state, so a fork must be merged by the runtime that writes to it. A merge that fails before its reservation is dispatched holds nothing and now returns its underlying error instead of `MERGE_RESUMABLE`; conflicting and unchanged merges leave the fork writable. A resumed or recovered merge re-reads the unchanged fork and rebuilds the same plan. Source bookkeeping advances each remaining changed original whose current path, metadata and content or vector the new version holds, so an interrupted pass can be repeated and a change that reached the fork in spite of the hold stays an unpublished change instead of being marked as published. A merge that reaches bookkeeping in the run that built its plan compares with that plan and sends no extra request; a resumed or recovered merge has no plan and reads the published version's tag once per 16 changed originals. The retention pass after a terminal merge still runs in the merge queue, now after the fork's queue is released. Statements that a fork stays writable during its merge or that edits made after capture stay on the fork no longer hold: such edits now wait for the merge and belong to the next one. `MERGE_SOURCE_NOT_READY`, `MERGE_SOURCE_CONFLICT`, the undocumented `MERGE_CAPTURE_UNCONFIRMED`, the merge-source case of `REF_CREATION_UNCONFIRMED` and the capture case of `STORE_BUSY` are removed. Retention cleanup now releases only superseded main version tags. An unfinished merge needs its fork branch to finish. The journal format changes without a compatibility path: a reservation no longer carries `sourceTag`, and the `merge-capture-v1` binding records are gone.
- Record a publication's affected file IDs in the journal when the merge publishes. The `completion` record of a published merge now carries at most 100 IDs in ascending order and a `fileIdsTruncated` flag, taken from the merge plan it applied, and `history()` builds each entry from the reservation and completion records it already reads. History no longer reads merge captures, automatic retention cleanup no longer writes a `history:<version>` archive before it releases a capture, and `HISTORY_UNAVAILABLE` is removed because it can no longer occur. Entries, their order and the 100-ID truncation are unchanged. The journal format changes without a compatibility path: a published completion without these fields is rejected with `INVALID_RESULT`.
- Read the publication journal on demand instead of replaying it into memory. A cold client finds the latest merge by a galloping search over reservation records with batched fetches, so opening costs a number of reads logarithmic in the number of merges and per-store memory no longer grows with them. Request replay and `MERGE_REQUEST_CONFLICT` detection use a request index record keyed by the hashed request ID. It is written once, after its reservation is confirmed and before the merge can reach a terminal record, so a request ID maps to one slot for the life of the store; an unfinished merge is matched as the journal head even before its index exists. Exact `version` selection, history cursors and history pages read reservation and outcome records directly by slot. Automatic retention cleanup works in merge order from a watermark stored in the journal that advances only past merges whose internal refs are confirmed released, and stops at the first merge still inside the window. Results, errors, cursors and recovery are unchanged. The journal format changes without a compatibility path: a journal written by an earlier unreleased build has no request index, so its requests would not replay.
- Hold the per-client store registry weakly. An idle drive is reclaimed after the application drops it, and `open` then builds a new object; a drive with running or queued operations, an unexpired list cursor, or a fence for an unconfirmed configuration, reference, write or merge outcome stays registered and is returned again. Expired list scans are now removed by one unreferenced timer instead of only by a later listing, so a cursor never keeps its store or client beyond its five-minute expiry.
- Remove compatibility with file stores created by earlier unreleased SDK formats. Managed stores require a persisted `chunking` configuration, which is now a required field of the managed `FileStoreDescription`, and declare the chunk embedding source with the native `sources` form (`[{ field: 'embeddingText', type: 'text' }]`) instead of the legacy `sourceField`; a store without either fails to open with `INCOMPATIBLE_STORE`. A text original without chunking provenance is rejected with `INVALID_RESULT`, publication always copies the fork's stored chunks and vectors, and a findText cursor issued for a main without a pinned version is no longer continued. Stores created by this SDK are unaffected, including a store whose creation was interrupted before its initial `v0` view was pinned.
- Reject a changed file original without a persisted `fingerprint` with `INVALID_RESULT` in `diff` and in merge preflight before main is changed, instead of accepting it as a file created by an earlier unreleased format; stores written by this SDK are unaffected.
- Add one-based inclusive `startLine` and `endLine` to each findText hit `range`, numbered with the same CRLF, CR and LF line breaks as ranged `read`, so a hit's lines can be passed to `read` to retrieve the lines containing the match. UTF-16 offsets and `context` are unchanged.
- Scan findText originals in ID-ordered batches of up to 16 per page with one native query, plus an exact read when resuming inside a file and the first live page's upper bound, instead of one query per original. Pages, hits, cursors and their validation are unchanged; large batches rely on the native client's automatic `docsUrl` download, and a response it leaves offloaded or whose document count disagrees with its total is rejected rather than treated as complete. New managed stores no longer create a text index on original `body` fields, which no query used, so originals are not analyzed on write; opening a store requires `body` to be unindexed. The chunk embedding source `embeddingText` is likewise stored without a text index: LambdaDB embeds an unindexed source field and keyword search matches chunk `content`.

- Separate the SDK history window from native snapshot retention. `retentionInDays` on `create`, `configure` and `describe()` now sets the window for superseded internal main version tags: integers from 1 to 365, default 30. New stores keep LambdaDB `snapshotRetentionInDays` at its one-day minimum and persist the window in the SDK configuration description in both embedding modes; `configure` writes both in one confirmed native update.

- Replace per-view handles with one drive object per store. Every request selects its view with a serializable `at` (`{ kind: 'main' }`, `{ kind: 'fork', name }` or `{ kind: 'checkpoint', name }`); omission means main. `write`, `diff` and `merge` require an explicit fork `at` and never fall back to main or create a fork. `fork` and `checkpoint` take an optional source `at` (with `version` only from main) and return `{ at }`. Add `listForks`, `listCheckpoints`, `deleteFork` and `deleteCheckpoint` methods and tools; `merge` only publishes and never deletes its fork. List, findText, read-range and history continuations are returned as `next` and forwarded unchanged; a cursor used with another view fails with `CURSOR_VIEW_MISMATCH`. findText and history cursors are now stateless opaque tokens that continue on any client of the same store and no longer expire after five minutes in SDK memory; a findText cursor becomes unavailable when its pinned version, fork or checkpoint incarnation, or resumed file is no longer available, and a history cursor only when it does not belong to the current store. List scan caches share one process-wide budget across stores and views, and keep their five-minute expiry. Shared tools are one-to-one with SDK methods and have one fixed schema set per embedding mode; the guide is version 7. Remove `MainFileDrive`, `WorkingFileDrive`, `CheckpointFileDrive`, `open({ at })`, `ForkSelection`, `CheckpointSelection`, `CreateMainFileRefRequest`, `FileRefEntry`, `FileToolRefResult`, handle `delete()`, view-bound tool schemas and the `REF_DELETED` error; a deleted fork or checkpoint reports `BRANCH_NOT_FOUND` or `CHECKPOINT_NOT_FOUND`.

- Default text search to semantic retrieval without reranking. Add explicit keyword and hybrid modes with independent reranking, preserve external-vector search, and explain mode selection in shared tools and the guide. LongMemEval and BEAM explicitly retain hybrid retrieval.

- Replace prerelease `asOf` ref selection with optional `version` on main fork/checkpoint creation. Select exact completed publications, reject version selectors on working forks/checkpoints and reject `asOf` everywhere. Preserve explicit checkpoint workflows and missing-history errors; update public types, tool schemas and the guide.

- Automatically enforce configured retention after terminal merges and completed recovery, preserving explicit forks/checkpoints, current main, bounded history summaries and request replay. Cleanup is bounded and best effort; remove the prerelease-only public pruning API.
- Configure retention at creation or through the drive, with generation checks, confirmed updates and fencing of unconfirmed configuration changes.
- Add persisted per-file chunking strategies and an optional local Docling Hybrid adapter, preserving exact originals, contextualized embeddings, verified ranges and parser-free publication recovery.
- Read bounded text ranges with exact line endings, Unicode-safe continuation and changed-original detection; expose the same contract through the shared read tool.
- List user forks and checkpoints, delete selected refs, and destroy stores with owned-journal cleanup and durable deletion recovery.
- Replace the memory SDK entry points with a file SDK for fresh stores, read-only main, and working forks.
- Create files in batches and read exact originals by path or stable file ID. Search indexed chunks with optional reranking and verified source ranges.
- Find case-insensitive literal occurrences in original file text with verified UTF-16 ranges, excerpts, metadata filters and resumable pages.
- Read the published main version, unfinished merge phase and paginated main publication history.
- Bind a shared file-tool catalog to a drive with an explicit allowlist, mode-specific JSON Schemas, unchanged file/publication results, optional fork and checkpoint creation, portable error formatting and a versioned read-only guide.
- Run LongMemEval against the public file SDK. The file-based corpus and run formats bind each evidence span to its original file and keep prior benchmark results on their original protocol.

## 0.1.0

First stable release of the standalone MemDrive SDK. The public API and storage
format are unchanged from 0.1.0-rc.1; the LambdaDB TypeScript client remains pinned
to 0.12.0.

- Provide memory storage, vector and hybrid retrieval, complete-original reads, metadata inspection, branches and portable agent tools.
- Wait for npm registry metadata to become visible after a successful publication, without retrying publication; verify archive identity and report channel state on reruns.
- Document stable installation and the `latest`, `rc` and `dev` channels.

## 0.1.0-rc.1

First release candidate of the standalone MemDrive SDK, backed by the pinned
LambdaDB TypeScript client 0.12.0.

- Store original memories with automatic text chunking, or store caller-provided embeddings and metadata.
- Retrieve evidence through vector or hybrid search with optional native reranking; support structured metadata filters, exclusions and ordered batch results.
- Read complete originals, inspect schema descriptions and keyword distributions, and manage memories and branches.
- Expose portable agent tools through `@functional-systems/memdrive/tools`, with JSON Schema contracts, branch binding and optional writes. Applications own search orchestration and answer generation.
- Support ESM, CommonJS and TypeScript consumers on Node.js 20.12+ and browser bundlers.
- Validate installed release archives with bounded live integration checks and publish immutable versions with source identity through npm Trusted Publishing.
- Supply the required Bayesian candidate budget when hybrid recall disables reranking.
