# Contributing

MemDrive is a standalone TypeScript SDK backed by the LambdaDB TypeScript client. It provides memory storage and retrieval; applications own answer generation and presentation.

## Development workflow

Use Node.js 20.12 or later and npm. Start new work from the latest `origin/main` in a dedicated task worktree, then submit a focused pull request targeting `main`. Continue related work in the existing task branch and worktree. Squash ordinary pull requests.

```sh
npm ci
npm run check:version
npm run lint
npm run typecheck
npm test
npm run check:package
```

`npm test` builds ESM and CommonJS distributions, compiles public TypeScript consumers and executes the unit tests. `check:package` packs the distribution, installs the tarball in an isolated temporary project with normal npm registry resolution, and checks ESM, CommonJS, TypeScript and browser consumers. These commands do not call a live database or model. Run `npm ci` first to install the pinned build and validation tools.

## Source and package boundaries

- `src/` contains browser-compatible SDK code. Use Web APIs in runtime code; keep Node built-ins in scripts and tests.
- `src/tools/` provides transport-independent tool definitions and execution through public SDK APIs. Keep model/MCP adapters and hosted service code outside this repository.
- `test/` contains unit regressions and public type consumers. Use small synthetic inputs without credentials or captured personal data.
- `scripts/` contains local version and distribution validation.
- `dist/` is generated by `tshy` and is not committed.

The public entry points are the package root, its `types` and `tools` subpaths, and `package.json`. Internal modules are not public exports. Tests may import built internal modules to cover implementation invariants, but examples and consumer checks use the public package name.

Keep retrieval as an SDK data operation. Query planning, repeated searches and evidence selection belong to calling applications or agents. Keep application-specific source preparation and answer assembly outside the SDK. Preserve error classification, request cancellation, branch and filter boundaries, and batch input/output correspondence when refactoring.

The LambdaDB dependency is pinned to an exact release. Update it deliberately with relevant API and regression checks. Tooling versions initially follow the native client's lockfile; updating tooling is separate from adopting a new database API.

## Validation and evidence

Add focused tests for distinct correctness risks. Public API changes need type-consumer coverage in addition to runtime checks. Avoid broad captured fixtures, private paths and credentials. Keep experiment outputs under ignored `artifacts/` and describe any live coverage separately.

A passing local suite establishes unit and package behavior only. `npm run test:live`
requires Node.js 24 and `LAMBDADB_BASE_URL`, `LAMBDADB_PROJECT_NAME` and
`LAMBDADB_PROJECT_API_KEY` in the environment or a local `.env.local`. It creates
and deletes three isolated test collections. Use a dedicated test project;
missing settings fail rather than silently skipping. The publication workflow
runs the live suite against the exact installed tarball. Document unperformed
checks accurately.

## Versions and releases

See [RELEASING.md](RELEASING.md). Development publication is manually dispatched from `main` and uses only the `dev` channel. A build or package check is not release authorization.
