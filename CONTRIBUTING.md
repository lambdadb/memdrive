# Contributing

MemDrive is a standalone TypeScript SDK backed by the LambdaDB TypeScript client. It provides file storage and retrieval; applications own answer generation and presentation.

## Development workflow

Use Node.js 20.12 or later and npm. Start new work from the latest `origin/main` in a dedicated task worktree, then submit a focused pull request targeting `main`. Continue related work in the existing task branch and worktree. Squash ordinary pull requests.

```sh
npm ci
npm run check:version
npm run lint
npm run typecheck
npm test
npm run check:package
```

`npm test` builds ESM and CommonJS distributions, compiles public TypeScript consumers and executes the unit tests. `check:package` packs the distribution, installs the tarball in an isolated temporary project with normal npm registry resolution, and checks ESM, CommonJS, TypeScript and browser consumers. These commands do not call a live database or model. Run `npm ci` first to install the pinned build and validation tools.

## Source and package boundaries

- `src/` contains the browser-compatible SDK. Use Web APIs in the core runtime. The optional `src/docling.ts` adapter is a separate Node-only entry point; do not import it from the package root.
- `test/` contains unit regressions and public type consumers. Use small synthetic inputs without credentials or captured personal data.
- `benchmark/` contains repository-owned evaluations outside the SDK. LongMemEval and original BEAM consume the public file SDK. File tools, model adapters and evidence scoring live in the benchmark. Keep datasets and run outputs under ignored `artifacts/`.
- `scripts/` contains local version and distribution validation.
- `dist/` is generated by `tshy` and is not committed.

The package root, `package.json`, and optional Node-only `docling` subpath are the public entry points. Use the public package name in examples and consumer checks. Keep application-specific conventions, model adapters and answer generation outside the SDK.

The SDK is a thin file abstraction over LambdaDB primitives: a store is one
collection, main and forks are branches and checkpoints are tags. Expose what
LambdaDB supports and keep the SDK free of state between calls: no caches,
locks, registries or internal collections. The one exception is the in-process
per-branch queue that runs state-changing calls one at a time, because a file is
several documents and LambdaDB has no multi-document transaction or conditional
write; its entries exist only while calls are pending. Ordering across processes
and multi-process ownership belong to the caller; document such limits plainly
instead of adding coordination. Features LambdaDB lacks, such as merge, history
or conditional writes, are not emulated in the SDK.

The Docling adapter uses pinned `docling.rs` as an optional peer. Package checks
first verify core consumers without that peer, then install it explicitly and
exercise the real Hybrid chunker with a small synthetic tokenizer. The fixture
checks integration and deterministic behavior, not retrieval quality. Preserve
exact originals, avoid invented ranges for rendered text, and reuse stored
chunks and vectors when moving files.

The shared file-tool catalog also lives at the package root. It is deliberately
minimal: six tools (`guide`, `read`, `list`, `search`, `findText`, `write`) on
main, without `at` in schemas, inputs or results, one fixed schema set per
embedding mode and an explicit allowlist. Each tool except `guide` calls the
public SDK method of the same name; refs, rollback and checkpoint retention stay
host operations. The optional host `checkpoint` hook makes every `write` call a
checkpointed write without exposing the checkpoint to the agent. Schemas describe JSON input while SDK validation enforces semantic
constraints. Schema tests use Ajv only as a development dependency. Keep guide
text independent of host authentication, product policy and provider adapters.
Change the shared guide `version` only in release pull requests, not for each
development change, but keep its text accurate for the current contract.
Development builds are identified by their package version and
`memdriveSourceCommit`, and evaluations record the exact guide text. The first
release containing the file-SDK guide resets its version to `1`; until that
release pull request, the current unreleased value stays unchanged.
The installed-package check exercises ESM, CommonJS, TypeScript and browser
imports, the tool catalog and a subset of the unit suites against the installed
archive.

## Validation and evidence

Add focused tests for distinct correctness risks. Public API changes need type-consumer coverage in addition to runtime checks. Avoid broad captured fixtures, private paths and credentials. Keep experiment outputs under ignored `artifacts/` and describe any live coverage separately.

A passing local suite establishes unit and package behavior only. `npm run test:live`
requires Node.js 24 and `LAMBDADB_BASE_URL`, `LAMBDADB_PROJECT_NAME` and
`LAMBDADB_PROJECT_API_KEY` in the environment or a local `.env.local`. It creates
and deletes isolated test collections, including a structured-text store. Use a
dedicated test project; missing settings fail rather than silently skipping. The
publication workflow runs the live suite against the exact installed tarball.
The default suite creates stores, forks them, writes on forks and on main,
reads, lists, searches and matches text, checkpoints a fork and rolls it back to
that checkpoint, deletes the refs it created (deleting a fork before its latest
checkpoint), and destroys every store, confirming each collection's deletion
with a native not-found response.

Opt-in flags extend it, each cleaning up what it creates:
`MEMDRIVE_RUN_LIVE_CHECKPOINT_TESTS=1` adds checkpoint conflicts and reads,
forking from checkpoints and forks, and another fork rollback to the basic store,
plus a separate store with checkpointed writes on main: it waits until a rollback
to the first checkpoint is accepted, reporting the delay, injects an alias
failure into the second checkpointed write and verifies the restore, and pages
`listCheckpoints`;
`MEMDRIVE_RUN_LIVE_EXTERNAL_VECTOR_TESTS=1` exercises external-vector writes,
filters and checkpoints in an isolated collection;
`MEMDRIVE_RUN_LIVE_FIND_TEXT_TESTS=1` verifies literal matching, live and
checkpoint cursors and continued scans across multiple native query pages in an
isolated collection. Document unperformed checks accurately.

The [model tool-use harness](benchmark/tool-use/README.md) consumes the shared
SDK tool catalog in an in-process host with explicit allowlists, main-only tools
and host-checkpointed writes. Keep its scenarios, provider transport and scoring outside `src/` and
the package archive. Its fixture/scripted tests run in ordinary CI without keys;
real model calls require explicit model mode and `LLM_API_KEY`. Scripted or
injected transports must never be reported as model performance, and fixture
results do not establish live LambdaDB or MCP wire behavior.
The manual **Model tool-use evaluation** workflow runs only from `main` and
passes the repository secret to the model step. Follow the benchmark run
instructions for pilot and full dispatches. Use the Actions summary and
short-lived JSON artifact for scoring and request diagnostics. Keep raw receipts
in the local workspace or on the ephemeral runner.

## Versions and releases

See [RELEASING.md](RELEASING.md). Main pushes never publish: they verify the derived dev version against dev when the committed version is tagged on origin, and otherwise verify the intended release against production. Authorized GitHub prereleases publish dev or RC versions, and authorized GitHub Releases publish stable versions. A local build or package check is not release authorization.
